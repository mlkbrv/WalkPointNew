# Deploying STRIDE for free

Enough to demo the whole thing end to end without paying anything. It is not a
production setup — the limits are listed under each piece, and they are real.

For a single paid VPS with TLS, nginx, and no cold starts, see
[`DEPLOYMENT.md`](DEPLOYMENT.md) instead.

| Piece | Where | Free tier |
|---|---|---|
| Postgres | **Neon** | 0.5 GB, no expiry, sleeps after 5 min idle and wakes in ~1 s |
| API | **Render** | 512 MB, sleeps after 15 min idle, cold start 30–60 s |
| Admin panel | **Cloudflare Pages** or **Netlify** | unlimited static hosting, no sleep |
| Mobile app | **Expo Go** | no build, no account limits |
| Redis | *not needed* | nothing in the code uses it yet |

Total cost: nothing. Total time: about 30 minutes.

---

## 1. Push the repository to GitHub

Both Render and Pages deploy from a repository, so this has to come first.

```bash
git init
git add .
git commit -m "STRIDE"
gh repo create stride --private --source=. --push
```

Check before pushing that no secrets are going with it — `.gitignore` already
excludes `.env`, but confirm:

```bash
git ls-files | grep -E "\.env$" && echo "STOP: a .env is staged" || echo "no .env staged"
```

## 2. Database — Neon

1. Sign up at [neon.tech](https://neon.tech) with GitHub.
2. Create a project (pick the region nearest your users).
3. Copy the **pooled** connection string from the dashboard. It looks like:

```
postgresql://user:pass@ep-something-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require
```

Keep it — Render needs it in the next step. The app rewrites this shape for
asyncpg itself (`app/core/config.py`, `normalise_database_url`), so paste it
exactly as Neon gives it.

Neon's free database does **not** expire. Render's own free Postgres does, after
30 days, which is why the database lives here instead.

## 3. API — Render

1. Sign up at [render.com](https://render.com) with GitHub.
2. **New → Blueprint**, pick the repository. Render reads
   [`render.yaml`](render.yaml) and proposes one Docker web service.
3. Fill in the two values it asks for:

| Variable | Value |
|---|---|
| `DATABASE_URL_OVERRIDE` | the Neon string from step 2 |
| `CORS_ORIGINS` | the admin panel URL from step 4 — leave blank for now, come back |

`JWT_SECRET` is generated by Render. Do not set it by hand, and do not change it
later: everything signed with it stays valid until it changes, and changing it
signs everyone out.

4. Deploy. The first build takes ~5 minutes. Migrations run automatically on
   start, so there is no separate release step.

You now have `https://stride-api-xxxx.onrender.com`. Check it:

```bash
curl https://stride-api-xxxx.onrender.com/health
# {"status":"ok","environment":"production"}
```

**There is nothing else to run.** The free plan has no shell — Render's Shell tab
is a paid feature — so the container bootstraps itself on start: migrations, the
default economy settings, the FAQ, and a superadmin account.

The account is `admin@example.com`. Render **generates** the password — it is
not in this repository, because a literal password here is a superadmin account
handed to anyone who can read the repo.

Read it once: Render dashboard → your service → **Environment** →
`BOOTSTRAP_SUPERADMIN_PASSWORD` → *Reveal*.

An existing account is never modified, so redeploys will not reset it. Change it
from the panel once you are in.

### What the free tier costs you

* **Cold starts.** After 15 minutes of no traffic the service stops. The next
  request waits 30–60 seconds. A demo link you send someone will be slow on their
  first click.
* **Uploaded media disappears.** The disk is wiped on every deploy and restart.
  Coupon images and story media survive until then and no further. Fixing that
  means implementing `Storage` for S3/R2 — see the end of this file.
* **Scheduled jobs stop while the instance sleeps.** `render.yaml` runs the
  scheduler in-process with a single worker, since the free plan allows only one
  service — but a sleeping instance runs nothing. Coins still accrue on every step
  sync, so the visible effect is a missing end-of-day notification. Fix it with an
  external cron, below.

## 3b. Scheduled jobs — an external cron (optional)

A sleeping instance runs no scheduler. The API exposes the jobs over HTTP so
anything that can make a request can drive them — free cron services, GitHub
Actions, or `crontab` on any machine you already have.

`render.yaml` generates a `CRON_SECRET` for you; copy it from the Render
dashboard (Environment tab). Without it these endpoints answer **404** — they are
off by default, and they do not advertise that they exist.

| Job | When |
|---|---|
| `POST /v1/jobs/daily-rollup/run` | once a day, after midnight in your timezone |
| `POST /v1/jobs/story-expiry/run` | hourly (or skip it: the feed already hides expired stories) |
| `POST /v1/jobs/voucher-expiry/run` | daily |

With [cron-job.org](https://cron-job.org) (free): create a job, method POST, add
the header `X-Cron-Key: <your secret>`. Or from any machine with cron:

```bash
0 1 * * * curl -fsS -X POST -H "X-Cron-Key: $STRIDE_CRON_KEY" \
  https://stride-api-xxxx.onrender.com/v1/jobs/daily-rollup/run
```

Each call also wakes the instance, so a daily ping doubles as a keep-warm.

The roll-up is idempotent and catches up: if a run is missed, pass the date and
it settles that day.

```bash
curl -X POST -H "X-Cron-Key: $KEY" \
  "https://stride-api-xxxx.onrender.com/v1/jobs/daily-rollup/run?day=2026-08-24"
```

On a real server none of this is needed — `docker-compose.yml` runs a `worker`
service that owns the schedule, and `CRON_SECRET` can stay empty.

## 4. Admin panel — Cloudflare Pages

1. [dash.cloudflare.com](https://dash.cloudflare.com) → **Workers & Pages** →
   **Create → Pages → Connect to Git**.
2. Pick the repository, then:

| Setting | Value |
|---|---|
| Framework preset | None |
| Build command | `npm run build` |
| Build output directory | `dist` |
| Root directory | `admin-panel` |

3. Add an environment variable — this is baked into the bundle at build time, not
   read at runtime, so it must be set **before** the build:

```
VITE_API_BASE_URL = https://stride-api-xxxx.onrender.com
```

4. Deploy. You get `https://stride-admin.pages.dev`.

**Now go back to Render** and set `CORS_ORIGINS` to that exact URL, with no
trailing slash. Without it the browser blocks every request and the panel shows
network errors that look like the API is down.

Netlify works identically — `netlify.toml` in `admin-panel/` already has the
build config and the SPA fallback.

## 5. Mobile app — Expo Go

No build and no store account. Install **Expo Go** on a phone, then:

```bash
cd mobile-app
echo "EXPO_PUBLIC_API_BASE_URL=https://stride-api-xxxx.onrender.com" > .env
npx expo start --tunnel
```

Scan the QR code. `--tunnel` means the phone does not need to be on the same
network as the laptop.

The laptop has to stay running — Expo Go loads the JavaScript from it. For a link
that works without your machine, `eas build` has a free tier, but it needs an
Expo account and takes ~20 minutes per build.

There is also a browser build (`npm run dev`), useful for checking API wiring
quickly. It is not the product: no real pedometer, no push, and tokens sit in
`localStorage` rather than the keychain.

## What to check once it is up

Work through this in order — each step depends on the previous one.

**API is alive**

```bash
curl https://stride-api-xxxx.onrender.com/health
curl https://stride-api-xxxx.onrender.com/v1/support/faq   # 4 seeded entries
curl https://stride-api-xxxx.onrender.com/v1/coupons       # [] until step 3 below
```

**Admin panel**

1. Open the Pages URL, sign in as `admin@example.com` with the password from
   Render's Environment tab.
2. Dashboard loads with all counters at zero. *If it shows a network error,
   `CORS_ORIGINS` is wrong.*
3. Economy → change the step threshold, save, reload. It persists.

**Partner onboarding and moderation**

4. Register a business:

```bash
curl -X POST https://stride-api-xxxx.onrender.com/v1/partners/register \
  -H "Content-Type: application/json" \
  -d '{"email":"cafe@example.com","password":"a-long-password","company_name":"Bean There"}'
```

5. In the panel: **Partners** shows 1 pending → Approve.
6. Sign out, sign in as `cafe@example.com` — you get the partner view, not the
   superadmin one.
7. Coupons → New coupon → Submit.
8. Sign back in as superadmin → Coupons → Approve.
9. `curl .../v1/coupons` now returns it.

**The app**

10. Open Expo Go, register an account.
11. Walk (or open the Health screen and use the dev mock) → the wallet balance
    goes up. Steps below the threshold earn nothing — that is the rule, not a bug.
12. Store → the approved coupon is there → buy it → the balance drops by exactly
    its price and a voucher appears in the wallet.
13. Wallet → tap the voucher → a redemption code.
14. Help → Message support → send a message.
15. Panel → Support → the thread is there → reply → it appears in the app.

**Anti-fraud**

16. Sync an implausible step count (over 35 000 in a day, or a large jump in a
    few minutes). The app reports it as under review and no coins are credited.
17. Panel → Flagged steps → the day is listed with the reason → Release coins →
    the balance moves.

If all seventeen work, the whole system works.

## Limits you will hit, in the order you will hit them

1. **Cold starts** — the first request after idle takes up to a minute. A cron
   ping every 10 minutes (cron-job.org, free) keeps it warm, at the cost of
   burning the 750 free instance-hours faster. The job endpoints in step 3b work
   as the ping.
2. **Uploaded media vanishes on redeploy.** Cloudflare R2 gives 10 GB free and
   speaks S3. It needs an `S3Storage` implementing `app/storage/base.py` — the
   interface is there and nothing above it knows where bytes live, but the class
   itself is not written.
3. **SMS sign-in does not send anything.** The code is written to the logs. A
   real provider goes behind `app/integrations/sms.py`.
4. **Push notifications do not send.** They still land in the in-app inbox.
   Firebase needs a service-account key.

None of these block a demo. All of them block a launch.

5. **Anyone with the API URL can register an account.** That is correct for a
   consumer app, but it means the demo is open. Nothing in the repository grants
   staff access — the superadmin password only exists in Render's environment.
